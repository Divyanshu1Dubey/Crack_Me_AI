## 2. Root cause: MARROW-style PUA-encoded fonts

The 19 subject-wise PDFs ("Anaesthesia pyqs.pdf", "Biochem pyqs.pdf", …) were generated by MARROW ED8 with a custom CMap font where every ASCII letter is mapped to a Unicode Private-Use-Area codepoint:

| Code range | Decoded to |
|---|---|
| U+E010 – U+E019 | "0" – "9" |
| U+E021 – U+E03A | "A" – "Z" |
| U+E041 – U+E05A | "a" – "z" |
| U+E008 – U+E00B | ".", ":", "(", ")" |

When opened in a PDF viewer, the CMap translates these PUA code points back to the visible ASCII glyph. PyMuPDF faithfully returns the *raw* code points (`page.get_text("text")`) because they ARE valid Unicode, so the strings looked like "0xE021" at rest, rendering as "A" on screen but "PUA garbage" in the DB.

The 6 year-wise PDFs (NEET-PG-2018/2020/2021/2022/2023/2025) use a standard Helvetica font and never exhibited this problem.

## 3. Pipeline walk-through

### 3.1 PDF text extraction (`importers/neetpg/pdf_reader.py`)

**Before:** `iter_pages()` called `page.get_text("text")` and returned the PUA string verbatim.

**After:** Same call, but `iter_pages()` pipes the result through `_decode_pua()`. The decoder is a pure-Python loop that maps PUA code points to ASCII in O(n) — verified against `Anaesthesia pyqs.pdf` page 1, which now decodes to:

```
Anesthesia AIIMS 2017
Question 1:
A 40 year old female with burns over her abdomen, both limbs and back and presented after
8 hours. Which of the following is the formula for calculation of fluid infusion?
a) 2 ml/kg X %TBSA for the next 16 hours
b) 5 ml/kg X %TSBA for the next 16 hours
c) 4 ml/kg X %TSBA for first 8 hours then 2 ml/kg X %TBSA for next 16 hours
d) 4 ml/kg X%TSBA for the next 16 hours
```

### 3.2 pdfplumber fallback (`pdf_reader.extract_text_via_pdfplumber_pages`)

Same decoder applied to per-page pdfplumber output.

### 3.3 OCR fallback

`importers/neetpg/ocr_engine.py` shells out to `tesseract`. **Tesseract is not installed in this environment** — every page that lacks a digital text layer + pdfplumber fallback yields empty text, no OCR, and (in the log) "Tesseract failed: tesseract is not installed". This is **TECHNICAL_DEBT.md P1 #4** and is required to extract any content from purely-scanned PDFs (none of the current corpus qualifies — all 25 PDFs have a digital or hidden-OCR text layer).

### 3.4 Parser (`text_parser.py::parse_page`)

No changes needed. Once PUA-decoded text reaches `parse_page()`, the existing regexes (`QUESTION_PREFIX`, `OPTION_PREFIX`, `ANSWER_LINE`, `EXPLANATION_LINE`) match correctly. The `OPTION_PREFIX = r"^\s*([A-Fa-f])[\.\)]\s+(.+?)\s*$"` regex matches `a) text`, `b) text`, etc. on its own line, which is exactly the MARROW format.

### 3.5 DB write (`db_writer.py::write_question`)

`update_or_create(recall_text_hash=text_hash, exam_type='neet_pg')` writes the decoded ASCII to `question_text`, `option_a`…`option_d`, `explanation`, etc. with `utf-8` collation (Postgres) or `utf-8` text encoding (SQLite). No double-encoding happens here — Django's parameter binding serialises Python `str` to UTF-8 bytes directly.

### 3.6 API / serializer (`serializers.py`, `recall_serializers.py`)

DRF `ModelSerializer` reads/writes the column as `str` (Python 3). JSON responses are encoded with `ensure_ascii=True` by default, which renders Greek letters, µ, ±, ≤, ≥ correctly as escape sequences. Frontend receives valid JSON.

### 3.7 Frontend (`FormattedText`)

`FormattedText` (a `react-markdown` wrapper) renders Unicode glyphs natively. Greek letters (µ, β, α, γ), super/subscripts (², ³, ⁻), and math symbols (±, ≤, ≥) all render correctly when present in the source.
