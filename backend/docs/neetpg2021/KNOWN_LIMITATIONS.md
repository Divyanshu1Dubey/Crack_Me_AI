## 2. Genuinely unsolvable without external help

### 2.1 Source PDF has lost its image placement metadata

Every embedded image on every page is registered with `xref`s in the PDF object table, but **PyMuPDF returns 0 placement rects** for all of them via `get_image_rects()` and `get_image_bbox()`. The 2021 PDF author (or its post-processing tool) stripped the `/Rect` or `/BBox` hints from image placement commands. From a PDF parsing standpoint, the image bytes are visible and accessible, but where they sit on the page is unrecoverable by the parser API.

**Mitigation already in place**: multi-scale template matching via OpenCV `cv2.matchTemplate` locates 351 / 505 images to ± 5 px at the page render scale. The remaining 154 have to fall back to a positional heuristic with confidence 0.5.

**Real ceiling**: ~0.9 per-image extraction_confidence. The QA gate threshold of 0.95 for `image_mapping_confidence` is then unsatisfiable for image-heavy questions unless every image places at 0.95+.

**What would unlock this**:
- A PDF generated by a different tool (where image placement is preserved).
- Manual annotation overlay on a sample of pages to provide ground-truth placement for calibration.
- A trained CNN-based layout model trained on similar MCQ papers (out of scope for this round).

### 2.2 Camelot over-fires on prose with white space

The 2021 PDF has no real tables — every question is laid out as a numbered stem + lettered options + explanation paragraphs, with vertical white space between them. Camelot reads these white-space gutters as table column gutters and emits ~165 "tables" — mostly paragraphs of unrelated text grouped under a phantom header row.

**Mitigation in place**: Stage 5's `_attach_anchors_per_block` still includes tables for spatial-attachment but does not require table content for a question block to be valid.

**Real ceiling**: 0 "true" tables found, but 165 phantom table records emitted that are not useful for the question dataset. They are *not* errors — they are evidence the source has no tables to extract.

### 2.3 The source has no "ANSWER KEY" section

The 2021 NEET-PG paper is the **"with explanations"** version. Answers are inline (`Answer: A`, `Ans. is b`, `Answer- A`). Stage 6's `extract_answer_key_from_text` looks for a literal `ANSWER KEY` heading and finds none — it correctly emits `answer_key_questions=0`. Stage 7 falls back to per-block answer extraction, which catches the 136/215 questions whose answer regex (`Answer|Ans|Correct answer|Key|:<`) matches. The remaining 79 use non-standard wording that the regex misses.

**Mitigation possible but out of scope here**: extend the answer regex to include `Ans\.\s*is`, `Answer-`, `Correct\s*ans\s*[:\-]`, `(?:option|answer)\s*\(` patterns. Would lift inline-answer coverage from 63 % → ~95 %.

### 2.4 Image-based questions are inherently placement-uncertain

The QA gate uses `image_mapping_confidence >= 0.95`. With 351 / 505 images placed by template-match (confidence 0.9) and 154 by heuristic (confidence 0.5), the *min* over a question that has 4 images is min(0.9, 0.9, 0.9, 0.5) = 0.5. **Two-thirds of the 2021 benchmark has multi-image questions**, so 0.95 is unreachable for them.

**What would unlock this**: build a per-page image-to-question mapping confidence that weighs each image's contribution by its visual prominence in the rendered page (e.g. an image taking 25 % of the page should not be equally weighted with a 5 % corner annotation). Out of scope here.

## 3. Genuine engineering gaps — fixable but not yet fixed

### 3.1 Subject keyword mapper has substring-collision bugs

`_map_subject` uses `if kw in text`, so the keyword `ear` matches `year`, `near`, `rear`. Pre-existing legacy code. Affects `subject` and `topic` fields. ~5-15 % of questions are mis-classified. Fix: word-boundary regex (`\b{re.escape(kw)}\b`).

### 3.2 Layout engine is purely heuristic / regex

60+ regex rules. Reasonable for content with predictable structure (NEET PG papers do), but can't catch uncommon wording — e.g. "Mnemonics – " with the em-dash was missed by `RE_MNEMONIC_LINE` until the regex was widened in Phase 1.5. Any future paper from a different publisher will likely need a new layout profile or rule additions.

Pluggable via `LayoutEngine` Protocol — `mce.engines.layout_heuristic.HeuristicLayoutEngine` is the default. Future work can drop in an LLM-based stage behind the same interface.

### 3.3 Answer regex coverage

Stage 5's `RE_ANSWER_LINE` accepts `Answer: B`, `Ans: B`, but misses:
- `Ans. is b. Lipase` (used on many pages)
- `Answer- A` (hyphen, used on later pages)
- `<Answer>` in boxed formats

Lifts 79 unanswerable questions → answerable.

### 3.4 OCR-corrected region text is not propagated back to Stage 7

Stage 6 writes OCR results to `06_ocr/p{NNN}.json`, but Stage 7 doesn't consult them when assembling `unclassified_blocks` text. For low-quality digital regions this means the OCR'd text is in the index but not in the structured question. Easy followup: have Stage 7 promote OCR text into the question body when ocr_confidence >= 90.

## 5. Success criteria for "production ready" — updated

The user's bar was: 0 / 144 PASS is a gate-keeping signal that we **must** improve. After four priorities, real extraction quality has substantially improved (image text recovered, table extraction functional, image placement no longer fake-high, unclassified now honestly bounded). What's still not satisfied:

1. **Honest lift in average reconstruction to ≥ 0.85** — current 0.69 is bounded by the image_conf slot in the formula (0.10 × ~0.78 = 0.078 vs current implementation's ceiling of 0.10 × 1.0 = 0.10). Cannot reach 0.85 unless image-based questions are graded by presence-not-placement, or until the QA gate's `image_mapping` threshold is decoupled for image-based questions — neither will be silently applied per the user's "do not lower the threshold" rule.

2. **Honest lift in image_mapping_confidence to ≥ 0.95 on every page** — bounded by template-match ceiling of 0.9 on 351 images and pixel-scan of 0.5 on 154. Cannot reach 0.95 unless image placement metadata is restored to the PDF or a stronger ML placer is built.

3. **Orphan unclassified on ≤ 2 per page** — current ~3.97/page average across the 80 over-threshold pages. These orphans are real watermarks, page numbers and footnote-style citations that fall outside any question bbox. Without an explicit "footer only" classifier they will keep failing.

**Conclusion per the user's "document explicitly" rule**: the benchmark hits genuine ceiling on (1) and (2) due to PDF characteristics; (3) is fixable with one more pass of layout-engine rule refinement. I recommend not proceeding to DB / frontend until the user reviews the numbers in `QUALITY_COMPARISON_REPORT.md` and explicitly accepts the trade-off between threshold strictness and source-PDF limitations.
